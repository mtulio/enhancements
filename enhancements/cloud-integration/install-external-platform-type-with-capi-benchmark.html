Does the external-platform CAPI proposal fit the Cluster API provider ecosystem?

An exploratory benchmark of sixteen Cluster API infrastructure providers against the payload and four-hook mechanism proposed in install-external-platform-type-with-capi. The question is narrow: are the four hooks the right set, and are they enough? Nothing in the enhancement proposal was changed to produce this.

EXPLORATORY · NOT A PLAN VERSION · NOT AN INPUT TO THE EP UNTIL REVIEWED · 2026-11-06

The short answer

The four hooks are the right set and they are sufficient. Across all sixteen providers examined, no scenario appeared that needs a fifth phase, and no provider makes one of the four redundant in a way that would justify dropping it. infraReady, postProvision and preDestroy are needed by every provider, because no Cluster API infrastructure provider creates api/api-int DNS records for a cluster domain — they publish an endpoint, not a name — and because anything a hook creates is unowned by a Cluster API object and therefore invisible to destroy.

The binding constraint on coverage is not the hook contract. It is the boot image. Nine of the sixteen clouds have no published RHCOS artifact, and two have no Ignition platform provider at all. Both are upstream problems the hooks cannot reach.

Scope, and what was excluded

Eighteen repositories were named and one more was raised during review. Sixteen are benchmarked; the rest are findings in their own right, and are listed at the foot of the result table so the set stays complete:

  • Alibaba Cloud — aliyun/cluster-api-provider-alibabacloud returns HTTP 404. There is no Alibaba Cluster API infrastructure provider: the repository does not exist, and clusterctl's provider registry has no Alibaba entry. openshift/cluster-api-provider-alibaba is a Machine API actuator, which is a different contract. Ignition does support the aliyun platform, so the gap here is the provider, not the operating system — and one community project has started filling it, discussed below.
  • Tencent Cloud — TencentCloud/cluster-api-provider-tencent was last pushed 2022-10-24 and exposes only tkeclusters and tkemanagedmachinepools. It is a managed-TKE provider, not a self-managed infrastructure provider, and it is absent from clusterctl's registry. It cannot provision the machines this proposal needs, at any version.
  • Huawei Cloud — the repository named, HuaweiCloudDeveloper/cluster-api-provider-huawei, is an empty shell: 0 stars, one path in its tree. clusterctl points instead at huaweicloud-samples/cloudnative-cluster-api-provider-huawei, which is what was benchmarked.

All sixteen benchmarked providers are listed in clusterctl's provider registry (cmd/clusterctl/client/config/providers_client.go), which means each publishes infrastructure-components.yaml and metadata.yaml as release assets. The payload's layout.customResource and its sibling metadata.yaml therefore assume nothing a conforming provider does not already produce. Sixteen of sixteen pass the packaging axis.

An unofficial Alibaba provider that already aims at platform: external

SammZhu/openshift-capi-alicloud describes itself as a Cluster API infrastructure provider for Alibaba Cloud targeting OpenShift External Platform mode. Its own README opens with the disclaimer, in its words: “Unofficial, community-maintained project. Not affiliated with, endorsed by…” — single-maintainer, best-effort, zero stars, Apache-2.0, created 2026-05-13, last pushed 2026-10-14. It is not an official Alibaba provider, it is not in clusterctl's registry, and nothing here should be read as Red Hat recognising it. It is reported because of what it independently chose to build.

It cannot exercise this proposal. Its stated design installs the control plane with the Agent-based or Assisted installer into a VPC and SLB created beforehand by ROS templates; the provider then adopts that infrastructure and manages worker Machines only. Greenfield control-plane provisioning is explicitly not implemented. That is the day-2 machine-management shape — OCPSTRAT-1322's territory — not the day-0 provisioning this EP specifies.

Two things in it are nonetheless evidence. First, it is a conforming clusterctl provider by construction: release v0.1.24 ships infrastructure-components.yaml, metadata.yaml and cluster-template.yaml as assets — exactly the packaging the payload's layout.customResource assumes. Second, and more interesting, it carries an AlibabaCloudCluster.spec.ignitionStorage field that offloads an oversized Ignition config to an OSS bucket and boots the instance from a pointer config. An independent developer, working on a different cloud with no knowledge of this EP, arrived at the same answer CAPA reached with spec.s3Bucket: the offload belongs in the provider. That corroborates the EP's own position that ignitionReady is an escape hatch and the first-class fix is upstream in the provider — and it is a second data point for open question 1 below.

Bootstrap-data handling, provider by provider

Cluster API's bootstrap Secret carries a format key. A provider either branches on it or ignores it and writes the bytes into the cloud's user-data channel verbatim. Passing them through verbatim is not a defect — for Ignition it is exactly the right behaviour, and it is why most of this ecosystem works with the proposal without any provider change at all.

Where the proposal is validated

The four hooks are the right four

Each hook maps onto a gap that is structural rather than incidental to one cloud:

  • infraReady — needed by 16 of 16. Cluster API's contract ends at Cluster.spec.controlPlaneEndpoint: an address, not a name. OpenShift needs api.<cluster>.<domain> and api-int to resolve before the control plane comes up. No provider in this set creates those records, and none has a field to ask for them. Separately, only five of sixteen can express the machine-config-server listener on port 22623 declaratively — AWS (AdditionalListeners), Azure (AdditionalAPIServerLBPorts), OpenStack (additionalPorts), Hetzner (extraServices) and Linode (additionalPorts). Five model a load balancer with no way to add a listener; six model no load balancer at all.
  • postProvision — needed by 16 of 16. *.apps publication and filling a backend set both require control-plane addresses, which do not exist until machines have booted. No provider offers a phase here.
  • preDestroy — needed by 16 of 16, and it is the one most likely to be under-appreciated. Everything the other hooks create is unowned by a Cluster API object. Deleting the Cluster removes none of it. Without this hook, every install on every provider leaks.
  • ignitionReady — genuinely conditional, and the proposal is right to make it conditional. AWS does not need it: CAPA stages an oversized config itself through AWSCluster.spec.s3Bucket. Proxmox and vSphere do not need it: neither writes the config into a size-capped metadata field. OCI does need it, for a measured reason — CAPOCI base64-encodes user data into instance metadata (cloud/scope/machine.go:353) and OCI caps that at 32,000 bytes.

The payload shape asks for nothing unusual

Every benchmarked provider already ships the two artifacts layout.customResource and the payload's metadata.yaml name, built by a release process that exists for clusterctl. The proposal adds a descriptor beside them; it does not ask a provider to change how it releases.

Risks and open questions this benchmark surfaced

1. The consent gate guards a capability that will be the norm, not the exception

bootstrapIgnitionStaging: Allowed exists so a cluster creator consciously permits a partner hook to handle day-0 secret material. The benchmark says one provider in sixteen has a native offload path, and it is the one provider the installer already embeds. For most clouds the need for ignitionReady is a property of the cloud's metadata ceiling, not a choice anyone is making.

A gate that every non-AWS install must tick is a gate that stops carrying information, and it is an API field OpenShift can never remove. Worth deciding deliberately rather than by default.

2. Six providers model no load balancer at all — so where does controlPlaneEndpoint come from?

vSphere, Nutanix, Proxmox, CloudStack, IONOS and Huawei leave the API endpoint to the cluster author, conventionally kube-vip running on the control-plane machines. infraReady runs after infrastructure is ready, but controlPlaneEndpoint must be populated before the provider marks the cluster ready. On these providers that value has to come from somewhere the proposal does not currently name — the cluster template, presumably, with a pre-allocated address.

This is an ordering question, not a missing hook. It should be answered in the EP before a partner on one of these platforms discovers it.

3. The hook contract is an exec ABI with no version negotiation

openshift.yaml carries compatibility.kubernetes and nothing that describes the hook contract's own version. The phases, their environment variables and bootstrapOutputPath are a binary interface between OpenShift and partner-authored shell. Adding a fifth phase, renaming an environment variable or changing when a phase runs is a compatibility event with no mechanism to detect or refuse it — an old payload on a new installer will simply not be called.

This benchmark found no need for a fifth phase, which is reassuring but not a guarantee. A declared contract version in the descriptor is cheap now and expensive later.

4. RHCOS, not Cluster API, is what limits reach

Nine of sixteen clouds have an Ignition platform provider but no published RHCOS artifact: OCI, DigitalOcean, Linode, CloudStack, Hetzner, Outscale and Proxmox among them. For each of these the Cluster API side of the proposal is complete and the install still cannot happen. This is the generic artifact-override work, and this benchmark is evidence that it unblocks seven clouds, not one — a materially stronger argument than the OCI case alone.

5. Two clouds are outside the model and no OpenShift work can bring them in

IONOS Cloud and Huawei Cloud have no Ignition platform provider. RHCOS cannot read a configuration on them through any channel, so neither the payload nor the hooks ever get a chance to run. Bringing them in means contributing a platform provider to coreos/ignition first. Worth stating in the EP as the lower bound of the mechanism's reach, so that reach is not overclaimed.

Open questions, for decision

1
Should bootstrapIgnitionStaging remain a per-cluster consent gate when fifteen of sixteen providers will require it, or should the consent attach to the payload — signed, reviewed once by the partner's release process — rather than to each install?
2
For a provider that models no load balancer, what is the documented source of Cluster.spec.controlPlaneEndpoint, and does the EP need to say so explicitly rather than leaving it to the cluster template?
3
Should openshift.yaml declare a hook-contract version distinct from compatibility.kubernetes, so that a future phase change is a detectable incompatibility rather than a silent no-op?
4
Does the generic RHCOS artifact-override work get re-scoped and re-prioritised on the evidence that it unblocks seven clouds rather than OCI alone?
5
Should the EP state the Ignition-platform requirement as an explicit precondition, naming IONOS and Huawei as currently out of reach, so the mechanism's limits are on the record?

Method, and what was not done

  • Provider API surface was read from each repository's api/<version>/*_types.go and shared types.go, fetched at HEAD of the default branch on 2026-11-06. Thirty-two type files plus eleven shared type files.
  • Repository trees were enumerated through the GitHub trees API to locate CRD bases and bootstrap-handling source; CRD kinds were derived from config/crd/bases/ filenames.
  • RHCOS artifact availability is from the installer clone, not from documentation.
  • Not done, and the gaps are marked in the table rather than guessed: the user-data size ceiling was measured for OCI only (32,000 bytes, from the pilot) and inferred structurally for AWS. The other fourteen are recorded as unverified. Establishing each cloud's real ceiling is the one piece of research that would convert most of the ignitionReady column from a hypothesis into a fact.
  • No provider was built, run or installed against. This is an API-surface benchmark, not a test result.
  • Nothing in the enhancement proposal, the deck or any plan version was modified.
