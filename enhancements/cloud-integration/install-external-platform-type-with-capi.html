Platform External · Day 0 Enhancement proposal
01 / 18

Enhancement proposal · provisional

Install platform External with a partner Cluster API provider

Platform External gives a provider a supported place for their own cloud components. This extends the same contract to day 0: the installer runs the provider's own Cluster API controller — out-of-tree, out-of-payload, on the partner's cadence.

author @mtulio reviewers @patrickdillon · @JoelSpeed · @elmiko approver @patrickdillon · API @JoelSpeed OCPSTRAT-3724 · SPLAT-2929

Motivation

Platform External already integrates a provider's cloud. Day 0 is the part it leaves out.

platform: external is the supported way a provider integrates OpenShift with their own components — their CCM, their CSI driver, their cloud — with no provider code in the release payload and no in-tree platform for Red Hat to maintain. What it specifies today is the running cluster. Installation stays on the agnostic path: the user supplies the infrastructure, and the installer takes it from there.

That is a deliberate boundary, and it has held well. The cost of it shows up once a partner already has the automation and still cannot use it.

For the partner

A working Cluster API provider is of no use at install time, so the provisioning burden lands back on them — as a UPI flow, an Assisted flow, or both.

For the admin

A materially different install experience from every integrated platform. Automation and mental model do not carry over.

For Red Hat

The alternative is in-tree special cases: permanent maintenance cost, and a ceiling on supported platforms set by team capacity.

OCI is the concrete driver, the gap is general. Any partner with a working Cluster API provider hits the same wall. OCPSTRAT-1322 covers the day-2 half — autoscaling, machine health checks. This is the day-0 half.

The shape

Three parties, one boundary

The decision that matters

Local paths proved it. The image is the proposal.

Both modes are implemented and both ran end to end. They are not two options being offered — they are one pilot and one product.

Local paths — the pilot's form

binaryPath and componentsPath point at a controller binary and a components bundle already on the installer host.

  • How the mechanism was first proved, on AWS/CAPA and then on OCI/CAPOCI
  • Awkward for automation: somebody has to put the files there first
  • No digest pinning, no mirroring, no pull authentication
  • Nothing to sign and nothing to version

Not the partner-facing form. Recorded under Alternatives; retained in the API as developer and CI scaffolding only.

Payload image — the proposal

One OCI image, published by the partner through their own release process, carrying everything: controller, components, both template trees, hooks, descriptor.

  • Pulled over the registry API with pullSecret
  • Digest-pinned, mirrorable, works disconnected via imageDigestSources
  • Signed and versioned by the partner's existing release process
  • A conforming payload needs no path configuration at all

This is what a partner ships.

The local mode was the transition, not the destination. It existed to answer "can the installer run a provider it does not embed?" — and once the answer was yes, every remaining question was about delivery: how does a partner publish this, pin it, mirror it, sign it, version it. Those questions have one answer, and that answer is an image.

The decision that matters

How the pilot turned into the image

The EP states the departure in three parts, and nothing else changes. Delivery becomes an OCI image, because paths have no publication, pinning, mirroring or authentication story and an image has all of them already. The payload describes itself, so the cluster creator wires no paths and an undeclared executable is rejected rather than merely noticed. Templates and day-0 manifests travel with the provider, as two trees, because they have different destinations and different lifetimes.

Everything the pilot proved carries over unchanged. The hook contract, the no-credentials boundary, the wrapper-script escape hatch, the single-object extra-manifest rule, teardown verified on a second cluster, and the three shared-code touches. The payload changes how a provider is delivered, not what the installer does with it — and Open Question 1 is now only whether the local-path form stays in the tree at all.

The contract

The whole partner contract is one stanza

install-config.yaml · image mode

platform:
  external:
    platformName: foo
    cloudControllerManager: External
    clusterAPI:
      name: foo
      controller:
        image:
          ref: quay.io/foo/openshift-capfoo@sha256:...
      # everything below defaults beneath
      # <install-dir>/capi-installer
      variables:
        FOO_REGION: us-east-1

What the image carries

  • bin/controller — the provider binary
  • infrastructure-components.yaml — CRDs, RBAC, webhooks
  • metadata.yaml — clusterctl contract version, verbatim
  • openshift.yaml — layout + Kubernetes compatibility range
  • cluster-api/ — templates for the local control plane
  • manifests/ — day-0 templates for the installed cluster
  • hooks/ — the lifecycle programs the payload declares

Everything defaults. A conforming payload needs no path configuration: capiInstallerPath defaults to <install-dir>/capi-installer and every other path defaults beneath it. Hooks are filled in per phase from the payload's own layout; setting one in install-config overrides that phase and only that phase.

The contract

The payload layout is clusterctl's, not a new one

Before inventing a format: every Cluster API provider already publishes these, because clusterctl requires them of a provider repository.

NeedExisting conventionVerified in
One components bundle infrastructure-components.yaml — a single file, which is why the field is a file and not a directory CAPA, CAPOCI
Declared contract version metadata.yaml, mapping each release series to a Cluster API contract (v1beta1, v1beta2) CAPA, CAPOCI — both published today
Manifest templates ${VAR} substitution, including ${VAR=default} and ${VAR:="default"} CAPOCI cluster-template.yaml

The residue is one small file. metadata.yaml says nothing about Kubernetes versions, and nothing about where the hooks or the controller binary live — neither concept exists upstream. openshift.yaml carries exactly that, shaped deliberately like metadata.yaml so the two read as a pair.

The contract

Pulling the payload adds no vendored dependency

The first implementation vendored a registry client. It worked, and it was removed — the cost was out of proportion to one platform's optional mode.

In-process registry clientoc image extract — proposed
Vendor cost 22,861 lines across seven modules, including docker/cli and containerd/stargz-snapshotter/estargz, to support ~1,500 lines of payload handling None. go.mod, go.sum and vendor/ are unchanged
Registry behaviour A second client in a binary that already has one — two opinions about mirrors, proxies and auth The same path the installer already uses on the baremetal and RHCOS flows, during this very phase
Cost taken — A runtime dependency on oc, checked with LookPath before anything is created and only when a payload is configured

One cost turned out to be a feature. oc image extract normalises every file to 0640, so the installer restores the executable bit from openshift.yaml — for the declared controller and hooks, and nothing else. An undeclared program in a payload is now unable to run rather than merely detected after the fact: the descriptor stopped describing what can run and became what makes it able to.

The contract

Four hooks, because the installer holds no credentials

On an integrated platform the installer creates the cluster's DNS itself. Here it cannot, and must not — so it calls out at the same point in the flow.

ignitionReady

Conditional, but not rare. Only for providers whose controller cannot stage an oversized bootstrap ignition itself — which, measured across sixteen providers, is eleven of the fourteen that can run Ignition at all.

CAPA can: the installer hands it the full ignition in a Secret and the controller uploads to AWSCluster.spec.s3Bucket. CAPOCI cannot — it base64-encodes user data into instance metadata (cloud/scope/machine.go:353), and OCI itself caps that metadata at 32,000 bytes against a bootstrap.ign of hundreds of KB. The cap is the cloud's, not the provider's: no such constant exists in CAPOCI, so the install fails at the cloud API with a message about metadata size and nothing that mentions Ignition.

The only hook whose output the installer reads back, via a bootstrapOutputPath the payload declares — which may not be named bootstrap.ign, so the installer's own artifact is never shadowed. Gated by an opt-in install-config field, platform.external.clusterAPI.bootstrapIgnitionStaging — an enum, so “signed payloads only” is a later third value rather than a second field.

infraReady

Publishes api and api-int. The one hook an install cannot do without.

Pointer ignition targets api-int:22623. With no record, bootkube fails at resolve-api-int-url — and the install dies 40 minutes later at the bootstrap timeout.

It is also the earliest point the provider's identifiers — OCIDs, subnet and LB ids — exist at all, so it is the only place the CCM and CSI config Secrets can be written. They cannot be day-0 manifests for exactly that reason. Same for load-balancer surface CAPI does not model: CAPOCI has no field for a 22623 listener, and only five of sixteen providers have one.

postProvision

Publishes *.apps. Cannot be done earlier, and the reason is structural: the wildcard points at a load balancer the cluster's own CCM builds, minutes into bootstrap, in response to a day-0 manifest.

Cluster.status.ready is narrower than OpenShift's idea of ready. The split is exact in the reference payload: infraReady creates the MCS listener, postProvision fills its backend set — because that means naming control-plane addresses, which do not exist until the machines boot. Too late for infraReady, too early to be day-2.

preDestroy

Removes all of it again — DNS, the wildcard, and any staged ignition object. Nothing a hook created is owned by Cluster API, so deleting the Cluster will not touch it — it would outlive the cluster that paid for it. The installer cannot sweep by tag either: it has no SDK for the partner's cloud.

So this hook is a standing obligation on the other three: every resource a hook creates is removed by preDestroy in the same increment that creates it. It runs before the delete, and it is the only teardown phase — no post-destroy hook is needed, precisely because Cluster API never knew these objects existed.

ignitionReady is the one departure from the pilot. The pilot could not express it as a hook: the bootstrap ignition is final before provisioning begins, and all three existing hooks fire after that. It had to wrap the installer in a three-phase shell script — create ignition-configs, offload by hand, create cluster — which worked only because the asset store re-reads a changed file from disk across process boundaries. Making it a hook collapses that back into one create cluster, and stops the mechanism depending on shared asset-store behaviour every platform relies on: the substitution happens inside the external path only, and <install-dir>/bootstrap.ign is never mutated.

Each hook gets paths, never documents. OPENSHIFT_INSTALL_INFRA_JSON is the whole mechanism: the installer cannot read a field off an AWSCluster because it has no AWSCluster type and must not acquire one. It copies the object out of its local control plane as JSON and lets the hook dig.

The flow

Where each party acts during an install

create manifests validate stanza→ pull payload→ extract + validate layout→ render both template trees
create cluster ignitionReady hook→ local CAPI control plane up→ provider starts→ apply Cluster + machines→ cloud provisions
infrastructureReady infraReady hook→ bootstrap→ postProvision hook→ wait for install-complete
destroy cluster read metadata.json→ rebuild local control plane→ preDestroy hook→ provider deletes

Validation happens before any side effect. A malformed stanza, a missing path, an unresolvable ${VAR}, a non-executable controller, an undeclared executable in the payload — all fail before a single cloud call. Known limitation: a variable that resolves to a wrong value still passes, and fails at the cloud API instead.

The flow

Day 0 manifests are how the cluster gets its cloud

The provider builds infrastructure. The cluster still needs a CCM, a CSI driver, and a provider-id on every kubelet — and none of that is installer code either.

The partner supplies

  • Cloud controller manager — without it, nodes never get their provider-id and Service type=LoadBalancer stays Pending forever
  • CSI driver, if the platform offers storage
  • An ingress Service, because on platform: external the ingress operator selects HostNetwork and creates only a ClusterIP

The installer does

  • Renders manifests/ from the payload into the day-0 extra-manifest set
  • Publishes a worker ignition Secret, so provider-created machines can boot
  • Refuses a multi-document extra manifest, so a second object fails loudly rather than being silently dropped
  • Generates no MachineSets — day-0 workers are Cluster API Machine objects, not a compute pool

A payload install and a hand-written one converge here. The rendered trees land exactly where hand-written ones would, which is what makes the two CI arms comparable in the first place.

Teardown

Destroy through the provider that created it

Cluster metadata records the provider, its source and its hashes, so destroy cluster can rebuild enough of the local control plane to delete through the same code that created everything.

Why it needs a hook too

Anything a hook created is outside Cluster API's ownership. A hosted zone, a record in a shared public zone, and a load balancer the cluster's own CCM built are all invisible to deleting the Cluster.

The rule on this pilot: each new resource ships with its teardown in the same change.

State is the contract

Hooks run minutes or hours apart in separate processes. OPENSHIFT_INSTALL_STATE_DIR is the only channel between them, and preDestroy deletes only what the others recorded creating — by id and by exact name, never by discovery.

That matters most for the shared public zone: a filter matching more than intended takes out somebody else's cluster.

Teardown is verified on a second cluster. Three teardown defects in the pilot were found only by creating a cluster after a previous one had been destroyed. A single create/destroy cycle is not evidence, and the acceptance criteria say so.

Evidence

The AWS arm cannot prove the central claim

Reviewers should hold the test plan to this standard, because it is the one place where a green job means less than it looks.

AWS · local paths

The installer embeds CAPA. A passing run cannot distinguish "ran the binary it was handed" from "ran the binary it already had".

Tests the ergonomics of the mechanism. Does not test the mechanism.

AWS · payload image

Different code from the install-config down, so a passing path arm says nothing about it. Its controller is built from CAPA source at a pinned ref rather than copied out of the installer.

Narrows the gap. Does not close it.

OCI · CAPOCI

CAPOCI cannot be embedded. This is the only arm that constitutes evidence for the enhancement's central claim.

Blocked for continuous CI on a published boot image, not on this design.

Evidence to date. Payload-image mode installed an AWS/CAPA cluster end to end — Install complete! in 38m20s, every cluster operator Available=True, no level=error. One create cycle on one provider: evidence that the mode works, not that it is finished.

Evidence

Sixteen providers say the hooks generalise. The boot image is the limit.

The contract was derived from two providers — a thin base for something partners build against. Read against the published API types of the sixteen most-used Cluster API infrastructure providers, the hooks held and the operating system did not.

RequirementOf sixteen providersConsequence
DNS for the cluster domain 0 create api or api-int records DNS is outside the Cluster API contract everywhere. infraReady, postProvision and preDestroy are needed by 16 of 16 — not a CAPOCI gap.
A listener on 22623 5 can declare it; 5 model a load balancer with no extension point; 6 model no load balancer at all For eleven providers the MCS listener is infraReady work by construction. The six with no load balancer follow the kube-vip pattern — and this proposal has no answer for them yet.
Offloading an oversized ignition 3 of the fourteen that can run Ignition need no help — CAPA's s3Bucket, vSphere's guestinfo, Proxmox's storage snippet ignitionReady is correctly conditional, and conditional is not rare: the other eleven hand the bootstrap bytes to a size-capped cloud metadata API.
A published RHCOS artifact 9 have none — and 7 of those nine already have a working Ignition platform This, not the hook design, is what limits the reach of the enhancement. The OS can boot and configure itself on those seven; only the artifact is missing.
An Ignition platform at all 2 have none — IONOS Cloud, Huawei Cloud No channel exists by which RHCOS can read a configuration there. No hook substitutes for it; this is the mechanism's hard lower bound.

What this validates

No provider needed a fifth phase. Every provider-specific shortfall landed in one of the four lifecycle points already proposed. That is positive evidence the hook set can be frozen at four for v1beta1 rather than left open — which removes the most likely reason a breaking version bump would ever be needed.

Two providers have independently reinvented the ignition offload in-provider — CAPA's s3Bucket and an unofficial AliCloud provider's ignitionStorage. Same design, different clouds, no coordination: the need is real and is not being solved once.

What it exposes

The contract's reach is narrower than the provider ecosystem suggests, and the narrowing is caused by something this enhancement does not own. Take the hook set as generalising well and the shipping story as gated on boot images.

Two consequences for review: the RHCOS artifact override is a prerequisite for any second provider rather than an OCI workaround, and the no-load-balancer case needs an answer before on-prem-like platforms can be claimed in scope.

What this is not. A documentary survey of published APIs, not sixteen installs. Only OCI's 32,000-byte metadata ceiling has been measured against a real bootstrap.ign. Researched and drafted by an AI agent (Claude Code, claude-opus-5), spot-checked rather than line-by-line verified by a human. No decision in the proposal rests on it — the benchmark reinforced the direction already taken rather than changing it.

Review

Three changes touch code integrated platforms run

Everything else is new packages on a path no integrated platform reaches. These three are where review attention belongs.

Unknown-kind fallback

A user-supplied AWSCluster has no compiled-in Go type, so the scheme rejects it and the pilot falls back to unstructured handling.

Done carelessly this turns a misspelled kind on an integrated platform from a loud failure into a silent one. Scoped to the external path and it warns — but the scoping is provisional, not chosen.

Extra-manifest handling

Shared asset code in pkg/asset/manifests/. The single-object rule is a deliberate API contract, not a bug.

CAPI robustness fixes

Seven bugs this work exposed in shared bootstrap code — including a decode error that echoed a manifest, which can carry a Secret.

Each must demonstrate, not assert. With the new field unset, behaviour is identical to main; a malformed manifest on an integrated platform still fails loudly. The evidence is a diff, not a sentence in a PR description.

Risks

Four risks worth naming out loud

A partner binary runs on the installer host

With the installer's privileges. Path, executable-bit and architecture validation happen first and the SHA-256 is recorded — but that does not make it trusted, and pretending otherwise would be the real risk. Same category as an untrusted Terraform provider.

Ignition staging hands a hook the day-0 secrets

An ignitionReady hook reads the complete bootstrap.ign: MCS TLS key, a CA key, the pull secret, the kubeadmin hash. No other hook sees anything comparable. No mitigation changes that — only its blast radius is bounded: bootstrap only, size and SHA-256 logged and never content, and the script ships in the same payload whose controller already runs with the installer's privileges.

The pre-signed URL it mints is equally credential-equivalent. Shortest workable lifetime, deleted at teardown, verified gone rather than assumed — and the teardown record holds the request's identifier, never its URL.

Support attribution

An install can now fail inside code Red Hat did not write. Provider name and artifact hashes are in metadata and logs. Whether something stronger than logs is needed is open.

Partner provider quality is unverified

Nothing checks that a supplied provider behaves correctly. Mitigation today: none. A conformance suite is an open question; the partner validation model is a deliverable of OCPSTRAT-3724 in its own right.

Trust boundary, stated plainly: the installer validates the payload's structure, not its content. It checks the layout is present and the compatibility range admits this release. It does not inspect, scan or attest the controller, the manifests or the hooks.

Open questions

What is genuinely undecided

The payload layout, templating syntax, variable vocabulary and validation strictness are settled. These are not.

Before Dev Preview ships

  • How is the unknown-kind fallback finally scoped? Restrict to external, validate against the CRDs actually present, or register partner CRDs into the scheme at runtime. The pilot does the first; the choice is not made.
  • Do we validate user-supplied providers, and how? A conformance suite is the obvious answer and nobody has scoped one.
  • How are failure modes surfaced? Logs only, or a path that explicitly signals the failing component is not Red Hat owned?
  • Teardown before metadata.json exists. An ignitionReady hook creates cloud objects before the installer has written the metadata destroy cluster reads. A run that dies in between leaves an orphaned object and a live pre-signed request with no record of either. Hook writes its teardown state first, or the installer writes metadata earlier — undecided.

Before GA

  • Who supplies the ingress and API endpoint addresses? Three plausible answers, not equivalent, and the platform's own character decides — which argues for permitting more than one. A fourth case has no answer at all: six of sixteen providers model no load balancer, so controlPlaneEndpoint is an input and infraReady runs too late to supply it.
  • Must partner CCM and CSI tag what they create? Teardown is not supportable without it.
  • Boot images. The capability exists in RHCOS; the published artifact does not — for nine of sixteen surveyed providers, seven of which already have a working Ignition platform. Blocks continuous CI for the second provider, and most of the ecosystem after it.
  • CSR approval. Pre-dates this work, applies equally to platform: none, has no owner. Only settled point: it is not the installer.

Already closed: whether the local-path form is partner-facing. It is not — the payload image is the proposed form, and the pilot's local form now sits under Alternatives. What is left of Question 1 is internal: whether the local-path form is removed before GA or kept as scaffolding. controller carries no sourceType discriminator today — it gains one only if a second supply form is ever accepted.

Graduation

Dev Preview → Tech Preview → GA

  • Mechanism implemented: API, hooks, metadata, teardown
  • AWS/CAPA installs and destroys unattended
  • Partner contract documented, with an honest statement of limitations
  • CI covers the reference arms
  • No-regression evidence per shared-code change
  • Behind a feature gate

Tech Preview

  • Open Questions 1, 2, 5 and 6 have written, agreed answers
  • The hook contract is declared permanent, or declared a bridge
  • Nothing waits on the shared networking EP, which is provisional and has no External owner

GA

  • A provider that is not embedded installs continuously in CI
  • Partner delivery, validation and support model agreed — recorded once, shared with OCPSTRAT-1322
  • Upgrade, downgrade and skew specified and tested
  • Support procedures and must-gather coverage

Nothing here is installed into the cluster, so there is nothing in it to upgrade. The partner provider runs only in the installer's local control plane and is gone before the install completes. From the upgrade machinery's point of view the result is an ordinary platform: external cluster.

Support

An install fails in one of four places, in order

1 · Validation

Malformed stanza, missing path, wrong architecture. Fails before any cloud call.

Red Hat

2 · Provider start-up

The controller exits immediately, typically on an unrecognised flag. /healthz never answers.

The most common first-time failure.

Partner

3 · Provisioning

infrastructureReady never becomes true. Detail is in the provider's own logs and status conditions.

Partner

4 · A hook

Non-zero exit fails the install with the hook's exit code and its last output lines.

Partner

Logged by path, source and SHA-256 — never by content. That rule is what makes attribution possible without turning the install log into a place secrets leak. metadata.json records the external platform and the provider name, so "was this path used?" is answerable in one look.

Summary

Red Hat ships the seam, not the provider

No partner code in the release payload. No cloud credentials in the installer. No provider-specific path anywhere in the design — it has been exercised on two providers, and neither got an exception.

The contract

One install-config stanza, four hooks, a clusterctl-shaped payload descriptor, and a validation model that checks structure rather than content.

The artifact

One OCI image the partner publishes, pins, mirrors and signs through their own release process, on their own cadence. Local paths were the pilot.

The evidence

Two providers, two supply modes, teardown proven on a second cluster — and an honest statement that the AWS arms test ergonomics while the OCI arm tests the claim.

A partner integrates without forking the installer and without getting code merged into the payload. Red Hat supports the contract and the mechanism. It does not support any partner's provider — and the design is built so that the line between them is visible in the log.
